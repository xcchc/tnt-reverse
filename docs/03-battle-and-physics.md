# 03 · 战斗与物理

客户端**不做弹道预测**：开火后服务端下发完整轨迹，客户端只渲染。所以想让客户端
画出正确的弹道，必须把服务端的物理模型算准。

**证据来源**：`data/traj_samples.json`（真实 Fire 广播里的 track + 对应 FireReq）、
`data/weapon_dump.json`（武器表内存快照）。

**标记**：✅ 已验证　◐ 部分完成　○ 未验证

---

## 1. 坐标系与角度

屏幕坐标，**y 轴向下**。角度 `theta` 是拨盘值：

```text
theta = 0      向右平射
theta = 90     竖直向上
theta > 90     左上（可以打负角度，即下射）
theta = 179.95 客户端挂机时的自动平射
```

位置同步用 `FloatReq{f1=X, f2=Y}`（varint），战斗内坐标是**世界坐标**，
不是屏幕像素。地面基线常在 y≈900，但真实地图有地形，见第 5 节。

炮口 = 角色坐标 + `MUZZLE * (cos θ, -sin θ)`，`MUZZLE = 28`。真实广播的
`track` 第一点就是炮口，不是角色脚下。✅

## 2. 弹道模型

每帧 @30fps，**先更新位置，再更新速度**：

```text
v0 = V0K * (force / 100)              force 是 0~100 的力度
vx = v0 * cos(theta)
vy = -v0 * sin(theta)                 屏幕坐标 y 向下，所以向上是负
we = WIND_MULT * wind                 风按"水平目标速度"处理

每帧：
    x  += vx
    y  += vy
    vx += K * (we - vx)               水平向风收敛
    vy += K * (0  - vy) + G           竖直向 0 收敛，再加重力
```

常数（来自 libgame 静态常量）：

| 名称 | 值 | 含义 |
|---|---|---|
| `K` | `0.0186951412` | 空气阻尼系数 |
| `G` | `4.28938354` | 重力加速度（px/帧²） |
| `V0K` | `144.787175` | 满力初速（px/帧） |
| `WIND_MULT` | `1.46643562` | 风→水平速度的换算 |
| `MUZZLE` | `28.0` | 炮口偏移（px） |

**顺序是硬约束。** 把"更新位置"和"更新速度"两步对调，在 `data/traj_samples.json`
的两发样本上残差会从 12.56px 涨到 35.31px：

```bash
python tools/ballistics.py
# battle4    n=11  angle=24.0   force=35.94  max_err=12.56px mean_err=7.80px
# battle4    n=7   angle=24.0   force=56.26  max_err=11.38px mean_err=6.28px
# shots=2 worst=12.56px tol=15px  PASS
```

### 2.1 为什么不要用"闭式解"手写

上面这个逐步递推有闭式解（`tools/ballistics.py` 里的 `track_closed_form`，
与逐步版**逐点严格相等**）：

```text
A = (1 - q^n) / K        q = 1 - K
B = n - A
x = x0 + MUZZLE*cosθ + vx0*A + we*B
y = y0 - MUZZLE*sinθ + vy0*A + (G/K)*B
```

但闭式解的推导容易漏项：重力在速度递推里是**常数累加**，不是初始速度的一部分，
正确形式必须把 `G/K` 乘在 `B` 上。漏掉这一项，中后段会系统性偏低 10–30px，
而且样本少的时候不容易发现。除非有回归测试兜底，否则直接用逐步版。

## 3. 常数是怎么定出来的

静态常量（K / G / V0K / WIND_MULT）来自 `libgame_arm64-v8a.so` 的数据段与反汇编，
不是拟合出来的猜值。拟合只用来**验证**这些常量对不对：

```bash
python tools/fit_ballistics.py
# shots = 2
# params: K=0.016208 G=4.4087 WIND_MULT=0.0000 V0K=148.5361 MUZZLE=27.907 vy_scale=0.9354
# residual: max=2.284px rms=0.938px
```

拟合能把残差压到 0.94px，但**拟出来的参数不能直接用**：

- 样本只有 2 发，且都是顺风，`WIND_MULT` 完全欠定（拟合结果直接跑到 0，显然不对）；
- `K` 与 `V0K` 高度相关，样本少时二者会互相补偿；
- 换个地图、换把武器，欠定参数立刻失配。

所以实现里一律沿用静态常量，拟合工具只作为"残差是否合理"的交叉检查。这是本仓库
唯一的拟合脚本，不参与运行时。

## 4. 力度反解

给角度和水平距离，求需要多大力度。`tools/ballistics.py::solve_target`：

```python
force_pct = solve_target(theta_deg, dist_ju, height_ju=0.0, wind=0.0)
```

距离单位是游戏里的"距离单位"（1 单位 = 82.5px），命中判定中心是**脚底上方 20px**
（`TY_UP`），不是脚下。实现做法是对方程做三分搜索求飞行帧数 `n`，再回代解出力度。

实测力度与蓄力时长的关系（按住开火键的秒数）：

```text
force ≈ 19.5 * hold_seconds - 2.7
2.0s → 35.94    3.0s → 56.26    1.5s → 26.54
```

蓄力速率约 19.5–20.3 力度/秒。✅

## 5. 地形

`server/terrain.py` 是一个可变形高度图：

- 每张图一条地面高度序列，分辨率 5px/格；
- 爆炸在落点雕出圆弧弹坑，坑深上限约为基线以下 220px，坑缘微微隆起 2px；
- 弹道碰撞走 `ground_fn(x)` 回调，所以后续炮弹会真的落进之前炸出的坑里；
- 悬浮平台用 `add_platform(cx, y, half_width)` 压平一段地面，角色站在台面上。

**状态：◐ 部分完成。** 服务端的地形与碰撞是通的，但客户端是否根据服务端数据
重绘地形，没有拿到确证——弱射打钻石平台时客户端看不到可见变形（爆炸特效和浮字正常）。
可能是图本身不可破坏，也可能是变形触发器还没找对。

## 6. 伤害与宝物

客户端 UI 里直接写着宝物的数值说明，§48 采集到了 13 件宝物的完整文案，
`server/combat_model.py` 按这些文案建模。

伤害公式的形状：

```text
dmg = round(武器基伤 × 攻击方增伤族 × 角度/风修正 × 目标减伤族)
```

- 武器基伤查 `data/weapon_dump.json`（我方默认武器约 420 量级）；
- 真录直击伤害量级在数百（一发 477 左右），范围溅射是恒定的 60/70/80；
- 伤害主要由攻击方决定，防守方防御影响很小。

宝物效果分族实现（距离增伤、逆风增伤、冻结、免死护盾、减伤、回血、残血增伤、
近身增伤、怒气、高抛、节拍器、吸血、计数器），每族的参数取自 UI 文案。

**状态：◐ 部分完成。** 公式形状与量级对上真录，但各族的精确系数只到"文案级"
精度，没有做逐件宝物的独立标定。

## 7. 战斗中的其它实测要点

- **风每回合、每行动者各自独立**，不是整局一个常量。3v3 里不同行动者的风不同。
- **风是行动方视角**：同一回合左右两端客户端收到的值互为相反数。下发时按
  每个客户端自己的视角给值。
- 直线弹（狙击类技能）**无重力无阻力**，`track` 是恒步长射线，与抛物线不同。
- 真实广播的 `track` 点数是 7–17 个不等，与飞行帧数一致，**没有插值**。
- 玩家自己的爆炸半径来自服务端 `fire.blast`（实测有 482），不在武器表里——
  它是爆炸范围，不是武器 id。
